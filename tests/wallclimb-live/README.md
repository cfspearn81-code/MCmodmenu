Real-client Wall Climb verification for Faster 1.5.0 on Minecraft 26.3/Fabric, connected to a disposable vanilla localhost server on 127.0.0.1:25568 as offline OP BridgeLive. It uses production player physics and normal keyboard-input key mappings. No velocity/position physics is replaced. The fixture supplies held keys/window focus and a simulated Auto Bridge hold-key read for that integration case. Setup/teleports/healing use normal OP commands. It observes incoming server position-correction packets without changing them.

The reference is a real ladder with Wall Climb off. A second case climbs a stone wall with the module on. Both hold forward for 120 ticks, release for 20 ticks of sliding, then hold sneak without forward movement for 20 ticks. The height samples match exactly (max delta 0.0); both rise 13.9944 blocks, slide 2.40768 blocks, and have zero sneak-hold displacement. These values are observations of Minecraft 26.3's actual ladder implementation, not hard-coded speed targets in the module. trajectories.json preserves the samples; the final comparison covers climb/slide/hold, before retreat. Backing away is separately checked to leave contact and restore ordinary falling.

Additional cases pass: disabled movement at a wall, diagonal wall travel, an inside corner, stepping onto a four-block ledge, a flat floor not counting as a wall, ordinary midair gravity (velocity below -0.5), Free Cam moving without climbing the body, and Auto Bridge enabled/held without its edge protection fighting Wall Climb. Every case records zero unexpected server corrections after setup. This proves behavior on this local vanilla server, not every server's custom movement rules. Source also preserves ordinary ladders/vines by only changing false onClimbable results, and clears cached world/player references on lifecycle changes.

Scene: force-load the area X=-16..48,Z=-16..16. Stone floor: X=-4..40,Y80,Z=-8..7. Clear X=-4..40,Y81..120,Z=-8..2. Build the tall wall X=-2..30,Y81..120,Z3. Real ladder column: X0,Y81..120,Z2,facing=north,waterlogged=false. Corner wall: X25,Y81..120,Z0..3. Short ledge: X33..35,Y81..84,Z3..6, with air above. The real ladder has a thin collision surface: its reference starts at 0.5,81,2.5 (outside that surface), while the stone-wall case starts at 8.5,81,2.69. Both touch their respective collision surface on the first forward-input tick. Starting inside a ladder's collision shape would invalidate the reference by trapping the player against upper ladder blocks. The two discarded fixture attempts exposed this scene issue; the final run starts outside both surfaces.

The GUI checks type wallclimb through KeyboardHandler, find one result, click the switch both ways and inspect the Movement layout with eight modules. Screenshots were visually inspected at 1280×720; copies are outside the repository at /workspace/previews/faster-1.5.0/.

To reproduce, compile src/ against the production client classes and Minecraft/Fabric dependency classpath using JDK25, copy the two JSON resources into a clean fixture classes directory and jar it. Launch runClient with -Dfabric.addMods=/absolute/path/to/fixture.jar in JAVA_TOOL_OPTIONS and --username BridgeLive; SDL_VIDEODRIVER=offscreen and ALSOFT_DRIVERS=null support a cloud software-rendered run. The fixture modifies test-client settings and the disposable player's position/health through server commands, samples all cases, writes /tmp/wallclimb-live/results.txt and trajectories.json, and stops after WALL CLIMB ALL CHECKS COMPLETE. Restore the floor/walls if other fixtures changed this world. The fixture is outside production source roots and never enters the release JAR. Standalone WallClimbSettingsTest compiles the settings source against tests/support stubs into a temporary directory and uses -Dtest.config for an isolated config path.
